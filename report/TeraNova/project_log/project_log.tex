\section{Purpose and scope}
% ==================================================================
This log records the work I carried out to take over the FPGA matrix-multiplication accelerator developed by the previous project group. The overall project goal is to determine whether moving the inverse-scattering calculations of TeraNova's metrology system to the FPGA, and accelerating them in hardware, improves the run time of the system. The work in this period focused on:
\begin{enumerate}[noitemsep]
  \item reproducing the previous group's Vivado and Vitis projects on my own PC;
  \item analysing their design and identifying its bottlenecks;
  \item restoring two IP cores that were missing from the hand-over, and making the PS--PL interaction robust;
  \item preparing a new hardware build;
  \item putting the project under version control (GitHub) so that both group members work on the same version;
  \item preparing the baseline measurement on the ZCU102 (measurement application and build package);
  \item simulating the complete PL data path, including the real HLS RTL, while the board was not available;
  \item designing and simulating the first improvement: a faster \code{matrix\_partitioner\_B}.
\end{enumerate}

All work was done in the workspace \code{C:\textbackslash PLD}; the files received from the previous group are kept unchanged in a separate folder.

\subsection{30 September 2026 -- Analysis of the previous design}
% ------------------------------------------------------------------
I analysed the HDL, HLS and C sources, the block design, and the timing and utilisation reports of the previous build. The design multiplies two $50\times50$ matrices of 64-bit integers in $5\times5$ blocks:
\begin{enumerate}[noitemsep]
  \item the CPU writes A and B into block RAM as 10\,000 single 32-bit transactions;
  \item \code{matrix\_partitioner\_B} reads the blocks element by element (4 clock cycles per element);
  \item \code{MatMul5x5} multiplies two blocks in one clock cycle (1\,257 DSPs);
  \item an accumulator sums 10 partial products per output block;
  \item \code{RAM\_INTERFACE} writes the results to the PL-side DDR4, from where the CPU reads them back one by one.
\end{enumerate}

\textbf{Main finding.} The design is dominated by data movement. Fetching one block pair takes about 100 cycles while multiplying it takes about 5, so the compute unit is idle about 95\,\% of the time. I estimated the end-to-end run at roughly 2.5--4\,ms, and estimated that the proposed improvements (burst transfers instead of CPU single writes, removing the partitioner's wait states, banked memory, data reuse, a narrower pipelined multiplier) could reduce this to roughly 30--50\,\textmu s. I also noted that the current accelerator is probably slower than a CPU-only implementation, and that the gain grows with matrix size.

\textbf{Deliverable.} A full report (\code{previous\_group\_analysis.tex}, saved in \code{C:\textbackslash PLD\textbackslash report}) with 14 numbered findings, cycle and resource budgets, proposed improvements and expected speed-ups. All figures in it are estimates pending measurements on the board.

\subsection{2 October 2026 -- Restoring the two IP cores}
% ------------------------------------------------------------------
\textbf{Decision.} Two options were considered: (A) re-package the generated HDL found in the project, or (B) rebuild the IPs from source. I chose \textbf{option B}, because:
\begin{itemize}[noitemsep]
  \item it gives the group editable source code instead of opaque generated HDL;
  \item the improvement plan requires changing \code{RAM\_INTERFACE} anyway;
  \item the old \code{RAM\_INTERFACE} handshake (plain \code{ap\_none} wires on a free-running block) was not a proper protocol and could capture a result block twice or miss one.
\end{itemize}

\textbf{\code{RAM\_INTERFACE} (rewritten in HLS).}
\begin{itemize}[noitemsep]
  \item Input is now an \code{hls::stream} with an \code{ap\_fifo} interface; this maps directly onto the accumulator's existing valid/ready signals (\code{C\_valid} $\rightarrow$ \code{data\_empty\_n}, \code{C\_ready} $\leftarrow$ \code{data\_read}).
  \item Elements are extracted with \code{.range()} instead of a C union; the inner loop is pipelined (II=1).
  \item \code{done} rises only after all writes of the last block are complete.
\end{itemize}

\textbf{\code{matrix\_partitioner\_B}.} The newest VHDL was recovered from the project's \code{ipshared} folder. Its ports are identical to the archived version, so it only needed re-packaging with core revision 4.

\textbf{Application update (\code{helloworld.c}).} Separate timing of BRAM load, PL compute, result read-back and CPU-only reference; a 1-second timeout with a GPIO fallback so the program can never hang silently; the start signal is now a toggle so the design can be run repeatedly; two complete runs per execution; build optimisation changed from \code{-O0} to \code{-O2}.

\subsection{29 October 2026 -- Preparing the baseline measurement}
% ------------------------------------------------------------------
The goal is to measure how fast the system currently is on the ZCU102, before any improvement. All improvements are then judged against these numbers.

\textbf{Two baselines.} The Vitis platform still points at the previous group's original export (\code{interrupt\_rerun.xsa} of 30 September). Programming and running the board needs no licence. So I planned two baselines:
\begin{itemize}[noitemsep]
  \item \textbf{Baseline 0:} the previous group's bitstream, unchanged. It can be measured as soon as the board is available.
  \item \textbf{Baseline 1:} the restored design (rebuilt \code{RAM\_INTERFACE}, partitioner revision~4), once Badr has built its bitstream. This is the reference for the improvements. Its PL compute time should agree with Baseline 0, because the data path did not change.
\end{itemize}

{\sloppy \textbf{Measurement application.} I wrote a measurement version of \code{helloworld.c} (\code{C:\textbackslash PLD\textbackslash baseline\textbackslash}\allowbreak\code{helloworld.c}). It does the same work as the normal application and uses only hardware names that exist in both the old and the restored design. Compared with the normal application it:\par}
\begin{itemize}[noitemsep]
  \item runs the PL 10 times instead of twice and prints minimum, average and maximum per phase;
  \item measures with 10\,ns resolution (the A53 generic timer) instead of whole microseconds;
  \item measures the cost of one PS$\rightarrow$BRAM write, one BRAM read and one PL-DDR4 read (``latency probes''), so the load and read-back totals can be explained;
  \item repeats the CPU-only reference and reports the cold and the best (warm-cache) time;
  \item detects \code{done} both by interrupt and by polling GPIO channel~2, so a compute time is measured even if the interrupt path does not work;
  \item prints one \code{CSV,} line per run for a spreadsheet, and the compiler optimisation level of the build.
\end{itemize}
Verification: it compiles without warnings at \code{-O0} and \code{-O2} against stub versions of the Xilinx headers, and its logic was tested against a simulated board in four cases: interrupt works, only GPIO works, nothing arrives, and one wrong result. Each case gave the expected output. It still has to be built in Vitis and run on the board. A \code{results} folder (with a README for the log files) is ready next to it.

\textbf{Build package for the licensed PC.} Badr only needs the Vivado side: \code{S7\_integration}, \code{ip\_repo} and \code{scripts}, at exactly \code{C:\textbackslash PLD}. His steps: rename his own old \code{C:\textbackslash PLD}, unpack the package, check Report IP Status, run \code{3\_build\_and\_export.tcl}, and save utilisation and timing reports (\code{report\_utilization}, \code{report\_timing\_summary}). He then sends back \code{interrupt\_rerun.xsa} and the two reports. On my side the Vivado project stays frozen until the \code{.xsa} comes back. Everything is written down in a separate step-by-step baseline guide.

\textbf{Correction to the setup guide.} After a platform update the bitstream is found in \code{interrupt\_rerun\_plat\textbackslash export\textbackslash}\allowbreak\code{interrupt\_rerun\_plat\textbackslash hw\textbackslash sdt\textbackslash}\allowbreak\code{interrupt\_rerun.bit}. \subsection{29 October 2026 -- Simulation of the complete PL data path}
% ------------------------------------------------------------------
Working from home without the board, I simulated everything inside the PL. The results are written up in a separate report (\code{report\textbackslash simulation\_report}, also as an Overleaf project).

\textbf{Testbenches.} The functional testbench \code{tb\_chain} and the HLS testbench already existed. I added (all in \code{C:\textbackslash PLD\textbackslash sim}):
\begin{itemize}[noitemsep]
  \item \code{tb\_chain\_perf}: \code{tb\_chain} plus passive monitors on every valid/ready handshake that count cycles per stage;
  \item \code{tb\_chain\_rtl}: the data path with the \emph{real} \code{RAM\_INTERFACE} RTL generated by Vitis HLS, writing through \code{m\_axi} into a new AXI4 memory model (\code{axi\_mem\_model.vhd}) with adjustable write-response latency $L$. With \code{RUNS=2} it does a second complete run without reset;

\end{itemize}

\subsection{29 October 2026 -- First improvement: a faster partitioner}
% ------------------------------------------------------------------
I wrote two drop-in versions of \code{matrix\_partitioner\_B} (\code{sim\textbackslash variants}). Both have the same entity, ports, block order and output packing as revision~4:
\begin{itemize}[noitemsep]
  \item \textbf{v5a:} revision~4 with \code{WAIT1} and \code{WAIT2} removed (2 cycles per element);
  \item \textbf{v5b:} pipelined fetch, a new BRAM address every cycle, each element captured two edges later (1 cycle per element).
\end{itemize}
Both need the BRAM read latency to be 1 cycle and the address multipliers to add no delay. I checked this in the \code{.xci} files of the block design. All four BRAMs have \code{C\_READ\_LATENCY\_B = 1} without output registers, and both \code{mult\_gen} instances have \code{C\_LATENCY = 0}.
